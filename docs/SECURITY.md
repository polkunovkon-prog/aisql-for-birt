# Безопасность и приватность данных

- **Статус:** действует с 18.10.2026 (M2); дополнено 19.10.2026 (0.3.0:
  метаданные схемы БД, правка отчёта) и 22.10.2026 (0.7.0: диаграммы и
  колонтитулы — те же правила: модель видит только ТЗ и метаданные)
- **Относится к:** плагин «ИИ-конструктор отчётов» (BIRT 4.7)

## Коротко

**Личные данные из базы в модель не уходят** — ни при создании отчёта, ни при
проверке результата. Модель видит только тот текст, который пользователь сам
набрал в панели (ТЗ и вопросы), и отвечает текстом (спецификация, SQL).
При работе со схемой модель может получить **имена таблиц и колонок** — но
только если пользователь сам оставил вставленный текст схемы в поле ввода.
Строки данных не читаются вообще. Данные из PostgreSQL читает движок BIRT при
рендере — напрямую с этой машины на базу, минуя ИИ-сервер.

## Маршрут данных при создании отчёта

```
пользователь ──ТЗ (текст)──▶ ИИ-модель ──JSON-спецификация (текст, SQL)──▶ плагин
                                                                             │ проверки
                                                                             ▼
                                                       .rptdesign (Design API BIRT)
                                                                             │ рендер
       PostgreSQL ◀──SELECT──── движок BIRT (локально) ──▶ PDF/HTML/XLSX (локальные файлы)
```

| Что | Маршрут | Уходит в модель? |
|---|---|---|
| Текст ТЗ и вопросы из панели | → ИИ-сервер (`llm.baseUrl`) | да (это текст пользователя) |
| Метаданные схемы БД (имена таблиц/колонок) | ‹кнопка «Схема БД…»› → поле ввода → текст ТЗ | только если оставлены в ТЗ |
| Спецификация и SQL | ← от модели, только текст | — |
| Пароль базы данных | диалог сборки → свойство `odaPassword` в `.rptdesign` | **нет** |
| Строки данных из БД | PostgreSQL → движок BIRT → файлы отчёта | **нет** |
| Результаты рендера и файлы отчётов | остаются локальными файлами | **нет** |
| Журнал аудита | `~/.ai-birt/ai-birt-audit.jsonl` | **нет** |

## Что уходит в модель

1. **Чат**: системная инструкция из настроек + история чата (то, что набирал
   пользователь, и ответы модели) + текущий вопрос. История обрезается по
   объёму (`ChatHistory`, по умолчанию 100 000 символов).
2. **Создание отчёта** («Создать отчёт…»): системная инструкция формата v0
   (`SpecPrompts`) + текст ТЗ из поля ввода. Если в ТЗ указаны подключение,
   пользователь БД, таблицы и поля — это описание уходит на ИИ-сервер.
   Пароль БД туда не входит (правило 5 в `SpecPrompts`).
3. **«Проверить соединение»**: только `GET /models` — список моделей сервера.
4. **Схема БД** («Схема БД…»): плагин читает у базы только метаданные
   (`DatabaseMetaData`: имена таблиц, представлений, колонок и типов; лимиты
   60×40) и **вставляет текст в поле ввода**. В модель этот текст попадает
   только как часть ТЗ, которую пользователь видит и может вырезать; сама
   кнопка никаких запросов к ИИ-серверу не делает. Строки данных не читаются:
   `DbSchema.read` вызывает только `getTables`/`getColumns`.
5. **Правка отчёта**: в модель уходят текущая спецификация (текст: имена
   полей, SQL, подписи) и замечание пользователя; данные и пароль — нет.

Все обращения к ИИ в коде — точки вызова `LlmClient`: чат, создание отчёта,
правка отчёта и проверка соединения в настройках. Других сетевых запросов
к ИИ-серверу у плагина нет.

## Что в модель не уходит

- строки данных из БД (фамилии, суммы и любые значения из таблиц);
- пароль базы: в спецификации поле `password` запрещено, диалог пароля
  показывается только при сборке; в файле отчёта пароль хранится в скрытом
  виде штатным механизмом BIRT (`odaPassword`) — так же, как его сохраняет
  сам дизайнер BIRT. При чтении схемы БД пароль можно сохранить в
  `~/.ai-birt/ai-birt.properties` (права `600`) галочкой «Сохранить пароль» —
  по умолчанию он не сохраняется; в журнал аудита пароль не пишется;
- ключ ИИ-сервера (`llm.token`): хранится в `~/.ai-birt/ai-birt.properties`
  (права `600`) и отправляется только самому ИИ-серверу в заголовке
  `Authorization`;
- содержимое файлов отчётов и результаты рендера.

## Защита от опасного SQL

Модель пишет SQL текстом, но выполнить его «как есть» нельзя:

- разрешены только `SELECT`/`WITH`; запрещены `INSERT`/`UPDATE`/`DELETE`,
  DDL и другие изменяющие команды (список — в `ReadOnlySql`), а также
  несколько операторов в одном запросе и запрос длиннее 20 000 символов;
- проверка выполняется до сборки: при нарушении файл не создаётся,
  пользователь видит причину по-русски;
- рекомендация: подключайте отчёт к базе пользователем с правами только на
  чтение — тогда «лишний» запрос всё равно ничего не изменит.

## Рендер и проверка результата

- рендер выполняет движок BIRT локально (JDBC → PDF/HTML/XLSX); кнопка
  «Просмотр…» рендерит PDF тем же движком на этой машине, а
  `Run → View Report` использует встроенный просмотрщик BIRT;
- автоматическая приёмка (`releng/m2-selftest.sh`) рендерит отчёт локально и
  проверяет строки данных и кириллицу в PDF — без ИИ-сервера;
- офлайн-тесты (`releng/test.sh`) работают с заглушечным HTTP-сервером;
- ни один шаг проверки не передаёт данные в модель.

## Границы: что зависит от пользователя

- текст, который пользователь сам вставляет в чат или ТЗ, уходит на
  ИИ-сервер — не вставляйте туда персональные данные без необходимости;
- канал до ИИ-сервера задаётся настройкой `llm.baseUrl` (по умолчанию —
  локальный сервер в сети; для внешних серверов используйте доверенный
  сервер и `https`);
- готовые файлы отчётов содержат данные — храните и передавайте их по
  правилам вашей организации.


## Агентный режим (1.0.0): маршруты данных

Агентная сборка инструментами (ADR-0003) расширяет контур — и сужает риск:

```
пользователь ──ТЗ (текст)──▶ [маскирование ПДн] ▶ [забор fence] ──▶ ИИ-модель
      ▲                                                                        │
      │                                        tool_calls (имя + JSON-аргументы)
      │                                                                        ▼
   чат ◀── прогресс/итог ── AgentSession ── ToolRegistry ──▶ DesignSession
                                      (политика предприятия,      (транзакции Design API,
                                       fail-closed, лимиты)       валидация, .bak, атомарная запись)
```

| Что | Маршрут | Уходит в модель? |
|---|---|---|
| ТЗ пользователя | → маскирование ПДн → забор → модель | да (маскировано, помечено) |
| Структура чужого отчёта (`report_inspect`) | имена, SQL, колонки, параметры | да (только метаданные, в заборе) |
| Схема БД (`db_schema`) | имена таблиц/колонок (лимиты 60×40) | да (только метаданные) |
| Результаты инструментов | ok/ошибка, имена элементов | да (текст, без данных) |
| Строки данных | движок BIRT → файлы отчёта локально | **нет** |
| Пароль БД | диалог → свойства источника в .rptdesign | **нет** (в tool-аргументах запрещён промптом и не нужен) |

Никакой XML в модель не уходит и от модели не принимается: изменения
происходят только через вызовы инструментов, чьи аргументы строго
проверяются (unknown-поля запрещены, SQL только SELECT/WITH) и применяются
штатным Design API в транзакции. Это закрывает LLM05 (Improper Output
Handling) и сужает LLM06 (Excessive Agency): у модели нет ни «сырого» XML,
 ни файловых операций.

## Enterprise-политика (ADR-0004)

Файл `~/.ai-birt/ai-birt-enterprise.properties` (права 0600 у администратора)
или путь из `-Daibirt.enterprise.policy=…`. Действует **fail-closed**: если
файл задан, но не читается — инструменты отключены, правка чужих отчётов
запрещена, маскирование и аудит включены.

| Ключ | Смысл |
|---|---|
| `injection` | режим защиты от инъекций: off/flag/strict (перекрывает настройку) |
| `tools.disabled` | список инструментов через запятую или `*` (все) |
| `agent.editExisting` | false — запрет правки существующих отчётов |
| `agent.maxIterations` | жёсткий потолок итераций агентного цикла |
| `pii.masking` | true — маскирование ПДн закреплено |
| `audit.lock` | true — журнал аудита нельзя выключить |
| `audit.syslog.*` | выгрузка аудита в SIEM (host/port/app/enabled) |

Политика только сужает полномочия: пересечение с пользовательскими
настройками — по более строгому значению.

| Пункт | Механизм плагина |
|---|---|
| LLM01 Prompt Injection | `PromptInjectionDefense`: режимы off/flag/strict; HIJACK-правила блокируют в strict; fence вокруг ТЗ и интроспекции; deterministic-валидация аргументов инструментов |
| LLM02 Sensitive Information Disclosure | маскирование ПДн перед отправкой; секреты не покидают машину; в интроспекции нет данных |
| LLM05 Improper Output Handling | вывод модели не исполняется: только строгие аргументы инструментов через Design API |
| LLM06 Excessive Agency | гранулярные инструменты; complete mediation в `ToolRegistry`; лимиты итераций/мутаций; политика fail-closed; необратимые операции (remove_element) отключаются политикой |
| LLM07 System Prompt Leakage | системный промпт не содержит секретов; попытки «reveal prompt» — HIJACK-правило |
| LLM10 Unbounded Consumption | лимит итераций (24 по умолчанию), лимит мутаций (200), таймауты запросов |

## Аудит и доказуемость (1.0.0)

- Каждая запись журнала: `seq`, `ts`, `host`, `user`, `app`, `session`,
  `function` (включая `tool.<имя>`), `decision`, `outcome`, `ms`, `model`,
  `error`, `detail`, `prev`, `hash` — SHA-256 цепочка: `hash = H(prev|seq|payload)`.
- `verifyChain()` (кнопка «Проверить целостность журнала» в настройках)
  перечитывает журнал и находит первую повреждённую/удалённую запись.
- Syslog-экспорт: UDP, формат RFC 5424-подобный (`<PRI>1 ts host app procid
  msgid [structured] msg`), severity warning для отказов/блокировок.
  Для TLS-транспорта (RFC 5425) используйте локальный релей (rsyslog).
- NIST SP 800-92: локальный журнал + централизованная выгрузка; рост
  журнала линейный по числу операций (обычно десятки на отчёт).
