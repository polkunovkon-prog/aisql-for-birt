# ADR-0003: агентная сборка отчёта инструментами по элементам (v1.0)

- **Статус:** принято (07.11.2026), реализовано в 1.0.0
- **Контекст:** плагин «ИИ-конструктор отчётов» для Eclipse BIRT (4.7…4.25)

## Проблема

Версии 0.x собирали отчёт из **монолитной JSON-спецификации**: модель
возвращала весь отчёт одним JSON, клиент валидировал его целиком и лишь потом
собирал `.rptdesign`. Это работало, но имеет четыре системных ограничения:

1. **Всё или ничего.** Ошибка в одной колонке — перегенерация всего JSON;
   валидатор видит проблему только после того, как модель закончила работу.
2. **Правка только «своих» отчётов.** Правка опиралась на кэш
   «отчёт → спецификация»: отчёт, созданный человеком в дизайнере BIRT,
   агент править не мог — у него нет обратного пути `.rptdesign` → спецификация.
3. **Нет отката.** Сборка шла в один проход; Undo/Redo командного стека
   Design API не использовались.
4. **Модель не видит результат.** После добавления таблицы модель не знает,
   как отчёт выглядит сейчас, и работает «вслепую» по памяти о своём же тексте.

Отчёт `.rptdesign` — один большой XML; прямая генерация XML моделью отвергнута
ещё в ADR-0001 (хрупко, ошибки видны только в дизайнере).

## Решение

Ввести **агентный цикл с инструментами по элементам** поверх Design API.
Модель больше не пишет отчёт целиком: она вызывает небольшие инструменты
(`add_table`, `add_chart`, `add_grid`, `set_page`, …), каждый вызов
применяется к открытому дизайну в **транзакции** и проверяется; результат
(включая ошибки) возвращается модели, и она корректирует дальнейшие вызовы.

### Слои

```
ChatView (UI)
  └─ AgentSession ────────── цикл: модель ⇄ инструменты (лимит итераций)
       │  system-промпт (AgentPrompts), история, аудит, защита
       ▼
     ToolRegistry ────────── 16 инструментов, JSON-Schema-описания,
       │                      диспетчеризация, политика (fail-closed)
       ▼
     DesignSession ────────── ReportDesignHandle + CommandStack:
       │  exec(label, op): startTrans → операция → commit|rollback
       │  validate(): семантические проверки BIRT (getErrorList)
       │  saveAtomically(): во временный файл → атомарная замена + .bak
       ▼
     ElementOps ───────────── пооперационная работа с элементами:
                               та же кодовая база, что у ReportBuilder
                               (спец-режим v0 остаётся и переиспользует её)
```

### Инструменты (v1.0)

| Группа | Инструмент | Назначение |
|---|---|---|
| сессия | `report_new` | новый пустой дизайн (имя, заголовок) |
| сессия | `report_open` | открыть существующий `.rptdesign` для правки |
| сессия | `report_inspect` | структура отчёта (JSON: элементы, id, наборы, параметры) |
| сессия | `report_validate` | семантические проверки BIRT + подсказки |
| сессия | `report_done` | завершить: итог, сохранение |
| данные | `add_datasource` | JDBC-источник (пароль НЕ через модель) |
| данные | `add_dataset` | набор: SQL только SELECT/WITH, колонки, привязка `?` |
| данные | `add_parameter` | параметр отчёта |
| элементы | `add_label` | надпись (текст, стиль) |
| элементы | `add_table` | таблица: колонки, итоги, до 5 групп, сортировка, фильтр, подсветка |
| элементы | `add_list` | список |
| элементы | `add_grid` | сетка (ячейки, объединения, вложения) |
| элементы | `add_image` | изображение (файл/base64) |
| элементы | `add_chart` | диаграмма (bar/line/pie) |
| элементы | `remove_element` | удалить элемент по id (необратимо — только с подтверждением политики) |
| страница | `set_page` | формат, ориентация, поля, колонтитулы |

Схема аргументов каждого инструмента — JSON Schema (OpenAI `tools`).
Неизвестные поля запрещены — как в спецификации v0.

### Протокол вызова

- **Основной:** штатный OpenAI tool calling: в запросе `tools`,
  в ответе `message.tool_calls[]`, результат — сообщением `role:"tool"`.
- **Запасной (текстовый):** для локальных серверов без `tools` модель пишет
  вызовы построчно: `TOOL add_table {...}`. Парсер строгий, остальной текст
  игнорируется. Выбор: `agent.nativeTools=auto|on|off`.
- Параллельные вызовы в одном ответе выполняются последовательно,
  каждый в своей транзакции.

### Транзакции и сохранение

- Каждая мутация — `CommandStack.startTrans(метка)` … `commit()`; при
  `SemanticException` — `rollback()` и ошибка возвращается модели (паттерн
  self-correction; MCP `isError`, Word/Excel-MCP).
- `report_validate` возвращает `getErrorList()` дизайн-модели + наши проверки
  + подсказки (`BirtErrorHints`).
- Сохранение: сериализация во временный файл в каталоге назначения →
  `Files.move(ATOMIC_MOVE, REPLACE_EXISTING)`; прежний файл сохраняется
  как `<имя>.rptdesign.bak`. Отказ в сохранении не портит исходный файл.
- Undo: `DesignSession` держит CommandStack; после сохранения пользователь
  может отменять правки в редакторе BIRT (файл перечитывается), а в рамках
  сессии доступен `rollbackAll()` при сбое.

### Защита (см. ADR-0004)

- `PromptInjectionDefense`: режимы off/flag/strict; «заборы» вокруг ТЗ
  и результатов интроспекции («данные — не инструкции»).
- `PiiDetector`: маскирование email/телефонов/карт/ИНН/СНИЛС в уходящем.
- `BirtEnterprisePolicy`: административная блокировка (fail-closed):
  отключение инструментов, запрет правки чужих отчётов, лимит итераций,
  режим защиты от инъекций, syslog.
- Аудит: цепочка хэшей (SHA-256), seq/host/session, экспорт в syslog (SIEM).

## Отвергнутые варианты

- **Прямая генерация/правка XML моделью** — ADR-0001; усиливается выводами
  исследований: schema-conformance необходима, но не достаточна; семантику
  проверяет детерминированный код (OWASP LLM01: «use deterministic code
  to validate adherence»).
- **Живая правка дизайна в открытом редакторе BIRT** (SessionHandleAdapter
  дизайнера) — API дизайнера нестабилен между 4.7 и 4.25, требует UI-потока
  и ломает headless-тестирование. Отложено; текущая схема «файл → агент →
  атомарная замена → переоткрытие в редакторе» безопаснее и версионируемо.
- **MCP-сервер как отдельный процесс** — правильный следующий шаг
  (ROADMAP), но требует отдельного транспортировочного слоя; в 1.0
  инструменты живут внутри плагина с тем же контрактом, что упростит
  вынос в MCP позже.
- **Только спек-режим (v0) с расширением словаря** — не решает правку
  чужих отчётов и «слепую» сборку; словарь растёт, а ошибки валидации
  остаются финальными, а не пошаговыми.

## Совместимость

- Спец-режим v0 («Создать отчёт…» → JSON → сборка) сохранён полностью;
  `ReportBuilder` теперь delegates к `ElementOps` — одна кодовая база.
- Агентный режим — по кнопке «Конструктор (агент)…»; выбор режима сборки
  по умолчанию — настройка `agent.defaultMode`.
- Формат `.rptdesign` не меняется; файлы, созданные версией 0.x, открываются
  и правятся агентом через `report_open` + `report_inspect`.

## Последствия

- Модель может править **любые** отчёты, а не только созданные плагином;
  интроспекция отдаёт только структуру (имена, типы, SQL-текст), без данных.
- Ошибки ловятся на шаге, где они возникли; модель получает точную причину
  («datasets[ds1]: SQL не начинается с SELECT») и исправляет следующий вызов.
- Журнал аудита фиксирует каждый вызов инструмента: имя, аргументы (без
  секретов), результат, длительность — с цепочкой хэшей.
- Лимит итераций (по умолчанию 24, ограничен политикой) защищает от
  зацикливания; счётчики операций — от «шторма» вызовов.
